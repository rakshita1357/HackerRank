# Evaluation report

_Generated by `python3 code/evaluation/main.py` on 2026-10-24._

## 1. What is measured

* **Public samples** - the 32 cases of `dataset/sample_output.csv` are the only labelled data. They are scored with the pipeline run on samples + evaluation requests together (so competing rows are resolved as in the real run) but **without** using the sample answers to pre-assign resources, i.e. the labels are held out.
* **Custom cases** - five hand-built, fictional cases with their own tiny datasets (`code/evaluation/custom_cases.py`).
* **Consistency checks** on all 550 requests: the evidence-derived states are cross-checked against the (untrusted) workflow log.

Definitions: *status accuracy* = `deletion_status` equal; *step* = (phase, system_id, resource_id, operation); *field accuracy* = a field equal on steps that exist in the gold answer (missing steps count as wrong); *sequence exact* = identical ordered list of steps; *sequence LCS* = longest common subsequence / longer length.

## 5. Failures found and improvements made

1. **Failure.** Accounts with a 404 / no identifiers and anonymised analytics rows could not be tied to a person through evidence alone (first prototype: 6 of 32 samples missing steps).  
   **Improvement.** Added activity-window inference: the workflow log rows (`DELETE_RECORD`/`ANONYMIZE_RECORD`) that fall around `reported_at`, whose result matches `reported_status`, that are not owned by someone else in the evidence, and that a compliant case must be able to *prove* in a citable file. Competing cases are solved together as an assignment problem (constraint propagation, then a deterministic tie-break).
2. **Failure.** SQL snapshots store `enabled` / `restore_allowed` as integers; `1 is True` is false in Python, so 118 live connectors were first read as compliant and several incomplete cases were reported `COMPLETE`.  
   **Improvement.** Booleans are normalised once at extraction time. A per-format table of (resource kind, evidence event, derived state) was added to catch any other mis-reads.
3. **Failure.** Support-replica rows (`contact_query_completed` + `deletion_marker_check`) were treated as message bodies (REDACT) instead of leftover records (DELETE) - sample case_10.  
   **Improvement.** Replica/contact-index rows are marked as records, not messages.
4. **Failure.** PDF / screenshot evidence produced nothing (cases 33-63 came out `COMPLETE` with no steps).  
   **Improvement.** Added an artifact reader (pdftotext + Tesseract, optional Gemini vision) that pins catalog link events to the artifact captured just before them, accepts aliases (statement number, file name, `user_17`) and derives the state from what is displayed.
5. **Failure.** A resource seen in an early snapshot but missing from a later exhaustive snapshot of the same batch was still reported as present (bundle `evidence_12` was exported *after* `audit_at`).  
   **Improvement.** Evidence files captured after `audit_at` are never cited; the snapshot capture time (not the export time) is used for linking, and omission from a later, citable, exhaustive snapshot proves removal.
6. **Failure.** Look-alike identities (`name.jr@`, `name-1@`) and the same user appearing in several cases at different times polluted rosters.  
   **Improvement.** Exact normalised identifier matching only (current + historical e-mail, SHA-256 of every e-mail, phones), and a per-case observation window [`requested_at` - 1 day, `audit_at`].
7. **Failure.** Identifiers quoted inside free text (custom case 1) and hash/phone scan hits were not used for linking.  
   **Improvement.** Message text and scan hits are scanned for e-mails, 64-hex hashes and phone numbers.
8. **Failure.** Resource ties: when two cases share the same reporting window and result class, the workflow log does not say which account/analytics row belongs to whom (a 54-pair probe of all features - case number, request date, duration, e-mail - predicts the order exactly 50% of the time).  
   **Improvement.** Kept as a deterministic, documented tie-break (earliest unassigned activity to the lowest case number) and made visible: the number of forced decisions is reported below. Public sample answers are used to pre-assign the rows the 32 sample cases already own.

## 6. Known limitations

* **Ambiguous assignments:** 94 account/analytics rows were assigned with the deterministic tie-break because the data does not distinguish interchangeable cases; roughly half of those are expected to be wrong.
* Retained audit records of cases whose compliant resources are not visible in any file cannot be discovered.
* Screenshot interpretation is OCR/keyword based (Gemini vision is used instead when `GEMINI_API_KEY` is set).
* With only 32 labelled cases the sample score is an optimistic estimate: several rules were derived from them.
